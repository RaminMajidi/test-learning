۱. هدف تست‌نویسی چیست و چرا اهمیت دارد

تست‌نویسی یعنی نوشتن کدی که به‌صورت خودکار بررسی می‌کند آیا بخش دیگری از کد، همان‌طور که انتظار داریم رفتار می‌کند یا نه. بدون تست، تنها راه اطمینان از درست کار کردن برنامه، تست دستی در مرورگر است که هم زمان‌بر است و هم قابل اعتماد نیست.

چرا تست می‌نویسیم؟

• جلوگیری از Regression: مطمئن می‌شویم تغییرات جدید، چیزی که قبلاً درست کار می‌کرد را خراب نکرده.

• Refactor با اطمینان: می‌توان ساختار کد را بازنویسی کرد بدون ترس از خراب شدن رفتار.

• مستندسازی زنده: تست‌ها نشان می‌دهند یک کامپوننت یا تابع دقیقاً باید چه رفتاری داشته باشد.

• کشف باگ زودتر: باگ‌ها قبل از رسیدن به کاربر واقعی و در همان مرحله توسعه پیدا می‌شوند.

• اعتماد تیمی: در تیم‌های بزرگ، تست‌ها تضمین می‌کنند کد یک نفر، کد نفر دیگر را خراب نمی‌کند.

۲. انواع تست‌نویسی

نوع تست چه چیزی را بررسی می‌کند مثال در React سرعت اجرا
Unit Test یک واحد کوچک و مجزا از کد (تابع، هوک، کامپوننت ساده) تست تابع sum() یا یک کامپوننت Button خیلی سریع
Integration Test چند واحد که با هم ترکیب شده‌اند و باید هماهنگ کار کنند فرمی با چند input که با هم submit می‌شوند سریع
End-to-End (E2E) کل برنامه از دید یک کاربر واقعی، در مرورگر واقعی باز کردن سایت، لاگین، خرید محصول (با Playwright/Cypress) کند
Snapshot Test مقایسه خروجی رندر شده با یک نسخه ذخیره‌شده قبلی تشخیص تغییرات ناخواسته در ساختار UI سریع
Static Type Check بررسی صحت تایپ‌ها قبل از اجرای برنامه (نه دقیقاً تست، ولی مکمل آن) خطاهای TypeScript در زمان کامپایل آنی
نکته

در پروژه‌های React معمولی، بیشترین ارزش از Unit و Integration تست‌ها به‌دست می‌آید، چون هم سریع اجرا می‌شوند و هم مستقیماً با ابزارهایی مثل Vitest و Testing Library نوشته می‌شوند. E2E برای سناریوهای حیاتی و مسیرهای اصلی کاربر (مثل فرآیند خرید) نگه داشته می‌شود، چون نگهداری‌اش پرهزینه‌تر است.

۳. هرم تست (Testing Pyramid)

یک راهنمای کلی برای تصمیم‌گیری در مورد اینکه «چقدر» از هر نوع تست بنویسیم:

E2E — تعداد کم، سناریوهای حیاتی
Integration — تعداد متوسط
Unit — بیشترین تعداد، سریع و ارزان

هرچه به سمت بالای هرم برویم، تست‌ها واقعی‌تر ولی کندتر و شکننده‌تر می‌شوند. هرچه به سمت پایین برویم، تست‌ها سریع‌تر و ارزان‌تر ولی محدودتر در پوشش سناریوهای واقعی هستند. تعادل درست معمولاً یعنی نوشتن تست‌های زیاد Unit، مقدار معقولی Integration، و تعداد کمی E2E روی مسیرهای حیاتی.

۴. ابزارهای اصلی در اکوسیستم React

ابزار نقش
vitest اجراکننده تست (test runner)، جایگزین سریع Jest که با Vite هماهنگ است
@testing-library/react رندر کردن کامپوننت‌های React در محیط تست و دسترسی به DOM آن‌ها
@testing-library/user-event شبیه‌سازی واقعی‌تر تعاملات کاربر (تایپ، کلیک، انتخاب)
@testing-library/jest-dom matcher های اضافه مثل toBeInTheDocument(), toHaveValue()
jsdom شبیه‌سازی DOM مرورگر درون Node.js برای اجرای تست‌ها بدون مرورگر واقعی
msw (Mock Service Worker) استاندارد صنعتی برای mock کردن درخواست‌های شبکه در سطح شبکه، نه دستی
Playwright / Cypress اجرای تست‌های E2E در یک مرورگر واقعی

فلسفه اصلی Testing Library

"Test the way your users use your app" — یعنی به جزئیات پیاده‌سازی داخلی (implementation details) کاری نداشته باش، فقط چیزی را تست کن که کاربر واقعی می‌بیند و با آن تعامل دارد.

۷. اولویت‌بندی Query ها در Testing Library

اولویت Query چه زمانی استفاده شود
۱ (بهترین) getByRole دکمه، هدینگ، لینک، فیلد ورودی — همان چیزی که screen reader می‌بیند
۲ getByLabelText فیلدهای فرم که label دارند
۳ getByPlaceholderText / getByText وقتی گزینه بهتری در دسترس نیست
۴ (آخرین راه) getByTestId فقط زمانی که هیچ‌کدام از موارد بالا جواب نمی‌دهد

نقش‌های پیش‌فرض تگ‌های HTML

تگ HTMLRole پیش‌فرض
&lt;button&gt;button
&lt;a href="..."&gt;link
&lt;h1&gt; تا &lt;h6&gt;heading
&lt;img&gt;img
&lt;ul&gt; / &lt;ol&gt;list
&lt;input type="text"&gt;textbox
ابزار دیباگ

اگر مطمئن نیستید چه role هایی در صفحه رندر شده وجود دارد: screen.debug() کل HTML را در ترمینال چاپ می‌کند.

۸. مثال عملی: تست فرم و تعامل کاربر

import userEvent from '@testing-library/user-event'
import { render, screen } from '@testing-library/react'
import { LoginForm } from './LoginForm'

it('should call onSubmit with correct values', async () => {
  const user = userEvent.setup()
  const handleSubmit = vi.fn()

  render(<LoginForm onSubmit={handleSubmit} />)

  await user.type(screen.getByLabelText('ایمیل'), 'ali@example.com')
  await user.type(screen.getByLabelText('رمز عبور'), '123456')
  await user.click(screen.getByRole('button', { name: 'ورود' }))

  expect(handleSubmit).toHaveBeenCalledWith('ali@example.com', '123456')
})
نکته مهم

همیشه قبل از هر تست userEvent.setup() صدا زده می‌شود، و هر عملیات تعاملی (type، click) باید با await فراخوانی شود چون به‌صورت async شبیه‌سازی می‌شود.

۹. مثال عملی: Mock کردن توابع با vi.fn

const handleClick = vi.fn()

render(<Button onClick={handleClick}>کلیک کن</Button>)
await userEvent.click(screen.getByRole('button'))

expect(handleClick).toHaveBeenCalledTimes(1)
expect(handleClick).toHaveBeenCalledWith(/* آرگومان‌های مورد انتظار */)

vi.fn() یک تابع «جاسوسی» (spy) می‌سازد که رفتار خودش را ندارد، ولی ثبت می‌کند چند بار و با چه آرگومان‌هایی صدا زده شده است. این برای تست کردن ارتباط بین یک کامپوننت فرزند و parent آن، بدون نیاز به اجرای منطق واقعی، بسیار کاربردی است.

۱۰. مثال عملی: تست async و درخواست‌های API

beforeEach(() => {
  vi.stubGlobal('fetch', vi.fn())
})

afterEach(() => {
  vi.unstubAllGlobals()
})

it('should display user data after successful fetch', async () => {
  vi.mocked(fetch).mockResolvedValue({
    ok: true,
    json: async () => ({ id: 1, name: 'رامین' }),
  } as Response)

  render(<UserProfile userId={1} />)

  // findBy چون داده به‌صورت async می‌رسد
  const name = await screen.findByText('رامین')
  expect(name).toBeInTheDocument()
})
Queryرفتار
getByTextفوری چک می‌کند، اگر نبود بلافاصله fail می‌شود
findByTextasync است، چند بار retry می‌کند — مناسب برای نتیجه async
queryByTextاگر نبود null برمی‌گرداند — برای بررسی «عدم وجود»
جایگزین بهتر: MSW

به‌جای mock دستی fetch، ابزار Mock Service Worker (msw) در سطح شبکه درخواست‌ها را می‌گیرد و پاسخ فیک برمی‌گرداند — به کد واقعی نزدیک‌تر و قابل‌نگهداری‌تر است.

۱۱. مثال عملی: تست کامپوننت با Context/Provider

اگر کامپوننتی از useContext یا از react-router استفاده کند، هنگام render آن باید Provider مربوطه را هم دور آن قرار دهیم، وگرنه با خطا مواجه می‌شویم. 

function renderWithTheme(ui: React.ReactElement) {
  return render(
    <ThemeProvider theme={'dark'}>
      {ui}
    </ThemeProvider>
  )
}

it('should render with the dark theme applied', () => {
  renderWithTheme(<Header />)
  expect(screen.getByRole('banner')).toHaveClass('dark')
})

یک الگوی رایج برای تمیز نگه داشتن تست‌ها، ساخت یک تابع کمکی renderWithProviders است که همه Provider های لازم (Theme، Router، Redux Store و...) را یک‌جا اضافه می‌کند تا در هر تست تکرار نشود.

۱۲. مثال عملی: تست یک Custom Hook

برای هوک‌هایی که مستقل از یک کامپوننت خاص هستند، به‌جای رندر کردن یک کامپوننت کامل، از renderHook استفاده می‌کنیم. 

import { renderHook, act } from '@testing-library/react'
import { useCounter } from './useCounter'

it('should increment the counter', () => {
  const { result } = renderHook(() => useCounter())

  act(() => {
    result.current.increment()
  })

  expect(result.current.count).toBe(1)
})
چرا act لازم است؟

وقتی داخل تست، مستقیم متدی را صدا می‌زنیم که باعث تغییر state می‌شود، باید آن را داخل act() بپیچیم تا React مطمئن شود همه به‌روزرسانی‌های مربوطه قبل از assertion بعدی اعمال شده‌اند.

۱۳. قوانین طلایی تست‌نویسی

۱. رفتار را تست کن، نه پیاده‌سازی را

به state داخلی، نام متغیرها یا جزئیات پیاده‌سازی وابسته نشو؛ فقط چیزی را تست کن که کاربر می‌بیند.

۲. اولویت با getByRole است

اگر همیشه مجبوری از getByTestId استفاده کنی، احتمالاً یعنی کامپوننت از نظر accessibility ضعیف است.

۳. اسم تست باید مثل مستندات خوانده شود

اگر تستی fail شد، باید فقط از روی اسمش دقیقاً بفهمی چه رفتاری خراب شده.

۴. هر تست باید مستقل باشد

تست‌ها نباید به ترتیب اجرا یا نتیجه‌ی تست دیگر وابسته باشند.

۵. Mock را کم و هدفمند نگه دار

فقط چیزهای خارج از کنترل تست (شبکه، زمان، API مرورگر) را mock کن، نه منطق خودِ کامپوننت.

۶. هم مسیر موفق و هم مسیر خطا را تست کن

تست کردن فقط happy path کافی نیست؛ حالت‌های خطا و edge case ها اغلب جایی هستند که باگ واقعی رخ می‌دهد.

۷. Coverage عدد بالا هدف نیست

رسیدن به coverage صد درصد به معنی نبود باگ نیست؛ روی مسیرهای پرخطر و منطق پیچیده تمرکز کن.

اشتباه رایج

تست کردن جزئیات پیاده‌سازی داخلی، مثل: expect(component.state.isOpen).toBe(true) — این نوع تست با هر تغییر داخلی کد می‌شکند، حتی اگر رفتار واقعی درست باشد.

۱۴. چک‌لیست نهایی قبل از commit

☐ اسم تست‌ها گویا و خوانا هستند
☐ از getByRole به‌جای getByTestId استفاده شده (در صورت امکان)
☐ تست‌ها به ترتیب اجرا یا به هم وابسته نیستند
☐ mock ها بعد از هر تست پاک/ریست می‌شوند (afterEach)
☐ هم حالت موفق (happy path) و هم حالت خطا تست شده
☐ برای عملیات async از await و findBy/waitFor استفاده شده
☐ هر Provider لازم (Theme/Router/Store) هنگام render اضافه شده

۱۵. MSW برای mock کردن API

MSW (Mock Service Worker) استاندارد صنعتی برای mock کردن درخواست‌هاست — برخلاف mock دستی fetch، درخواست‌ها را در سطح شبکه می‌گیرد، یعنی به کد واقعی نزدیک‌تر است.

نصب

npm install -D msw

تعریف handler ها — src/mocks/handlers.ts

import { http, HttpResponse } from 'msw'

export const handlers = [
  http.get('/api/users/:id', ({ params }) => {
    const { id } = params

    if (id === '999') {
      return new HttpResponse(null, { status: 404 })
    }

    return HttpResponse.json({
      id: Number(id),
      name: 'رامین',
      email: 'ramin@example.com',
    })
  }),
]

راه‌اندازی سرور برای تست — src/mocks/server.ts

import { setupServer } from 'msw/node'
import { handlers } from './handlers'

export const server = setupServer(...handlers)

فعال‌سازی در src/test/setup.ts

import '@testing-library/jest-dom'
import { server } from '../mocks/server'

beforeAll(() => server.listen())
afterEach(() => server.resetHandlers())
afterAll(() => server.close())

تست تمیز و بدون vi.stubGlobal

it('should display user data after successful fetch', async () => {
  render(<UserProfile userId={1} />)
  expect(await screen.findByText('رامین')).toBeInTheDocument()
})

it('should show error for a non-existent user', async () => {
  render(<UserProfile userId={999} />)
  expect(await screen.findByRole('alert')).toHaveTextContent('کاربر پیدا نشد')
})
مزیتتوضیح
نزدیک‌تر به واقعیتدرخواست واقعی در سطح شبکه گرفته می‌شود، نه جایگزینی تابع
قابل استفاده مجددهمان handler ها در تست و در dev mode قابل استفاده‌اند
تمیزترنیازی به beforeEach/afterEach دستی برای fetch نیست
مستقل از کتابخانهچه fetch چه axios، فرقی نمی‌کند
Override کردن در یک تست خاص 
import { server } from '../mocks/server'
import { http, HttpResponse } from 'msw'

it('should handle server error', async () => {
  server.use(
    http.get('/api/users/:id', () => new HttpResponse(null, { status: 500 }))
  )

  render(<UserProfile userId={1} />)
  expect(await screen.findByRole('alert')).toBeInTheDocument()
})

۱۶. vi.mock برای mock کردن یک module

گاهی باید یک module کامل local (نه یک درخواست شبکه) را جایگزین کنیم — مثلاً یک فایل helper که با یک SDK خارجی کار می‌کند.

کد اصلی — src/lib/analytics.ts

export function trackEvent(name: string, payload: object) {
  window.analytics?.track(name, payload)
}

کامپوننت — src/components/BuyButton.tsx

import { trackEvent } from '../lib/analytics'

export function BuyButton() {
  function handleClick() {
    trackEvent('buy_clicked', { source: 'homepage' })
  }
  return <button onClick={handleClick}>خرید</button>
}

تست

import { trackEvent } from '../lib/analytics'

// کل ماژول را mock می‌کنیم؛ همه export هایش خودکار vi.fn() می‌شوند
vi.mock('../lib/analytics')

it('should track event when buy button is clicked', async () => {
  const user = userEvent.setup()
  render(<BuyButton />)

  await user.click(screen.getByRole('button', { name: 'خرید' }))

  expect(trackEvent).toHaveBeenCalledWith('buy_clicked', { source: 'homepage' })
})
vi.mock باید hoisted باشد

Vitest به‌صورت خودکار فراخوانی vi.mock(...) را به بالای فایل منتقل می‌کند (قبل از import ها اجرا می‌شود)، ولی بهتر است همیشه بالای فایل نوشته شود تا خوانا بماند.

ابزارچه زمانی استفاده شود
MSWوقتی چیزی که mock می‌کنید یک درخواست شبکه (HTTP) است
vi.mockوقتی چیزی که mock می‌کنید یک ماژول/فایل local است (SDK، helper، کامپوننت فرزند سنگین)

۱۷. کنترل زمان با Fake Timers

کامپوننت — src/components/Toast.tsx

export function Toast({ message }: { message: string }) {
  const [visible, setVisible] = useState(true)

  useEffect(() => {
    const timer = setTimeout(() => setVisible(false), 3000)
    return () => clearTimeout(timer)
  }, [])

  if (!visible) return null
  return <div role="status">{message}</div>
}

بدون fake timer، باید واقعاً ۳ ثانیه در تست صبر کنید. با fake timers می‌توانید زمان را جلو ببرید: 

import { act } from '@testing-library/react'

describe('Toast component', () => {
  beforeEach(() => {
    vi.useFakeTimers()
  })

  afterEach(() => {
    vi.useRealTimers()
  })

  it('should disappear after 3 seconds', () => {
    render(<Toast message="ذخیره شد" />)

    expect(screen.getByRole('status')).toBeInTheDocument()

    // زمان را ۳ ثانیه جلو می‌بریم، بدون صبر واقعی
    act(() => {
      vi.advanceTimersByTime(3000)
    })

    expect(screen.queryByRole('status')).not.toBeInTheDocument()
  })
})
چرا act() اینجا لازم است؟

اجرای setTimeout توسط advanceTimersByTime باعث صدا زده شدن setVisible(false) بیرون از یک event handler عادی React می‌شود. بدون act()، تضمینی نیست که re-render ناشی از این تغییر state قبل از خط expect بعدی روی DOM اعمال شده باشد — نتیجه‌اش خطایی شبیه expected document not to contain element, found <div role="status"> است، حتی وقتی منطق کامپوننت کاملاً درست است.

ترکیب با userEvent

اگر در همان تست هم از userEvent و هم از vi.useFakeTimers() استفاده می‌کنید، باید موقع setup این را هم مشخص کنید، وگرنه await user.click(...) ممکن است گیر کند: 

const user = userEvent.setup({ advanceTimers: vi.advanceTimersByTime })
کنترل تاریخ سیستم

اگر کامپوننت از Date.now() هم استفاده کند، با vi.setSystemTime(new Date('2026-01-01')) قابل کنترل است.

۱۸. تست‌های پارامتری با it.each

وقتی چند ورودی مختلف همان منطق را تست می‌کنند، به‌جای کپی-پیست از it.each استفاده کنید: 

describe('isEven', () => {
  it.each([
    [2, true],
    [3, false],
    [0, true],
    [-4, true],
    [-7, false],
  ])('isEven(%i) should return %s', (input, expected) => {
    expect(isEven(input)).toBe(expected)
  })
})

خروجی این‌طور می‌شود، هر ردیف یک تست جدا حساب می‌شود:

✓ isEven(2) should return true
✓ isEven(3) should return false
✓ isEven(0) should return true
✓ isEven(-4) should return true
✓ isEven(-7) should return false

برای object های پیچیده‌تر، از یک آرایه از object ها استفاده کنید:

it.each([
  { email: '', password: '123456', expectedError: 'ایمیل الزامی است' },
  { email: 'a@b.com', password: '', expectedError: 'رمز عبور الزامی است' },
])('should show "$expectedError" when email is "$email"', async ({ email, password, expectedError }) => {
  // ...
  expect(screen.getByRole('alert')).toHaveTextContent(expectedError)
})
چرا مفید است؟

از تکرار کد جلوگیری می‌کند، مخصوصاً برای validation های فرم که چندین حالت خطا دارند.

مثال دوم (کامل و جداگانه): تست پارامتری اعتبارسنجی فرم لاگین

در مثال قبل فقط ساختار کلی it.each با object را دیدیم. این‌بار یک سناریوی واقعی و کامل را پیاده می‌کنیم: یک فرم لاگین که باید پیام خطای جداگانه برای خالی بودن ایمیل و خالی بودن رمز عبور نشان دهد.

کامپوننت — src/components/LoginForm.tsx

import { useState } from "react";

type LoginFormProps = {
  onSubmit: (email: string, password: string) => void;
};

export function LoginForm({ onSubmit }: LoginFormProps) {
  const [email, setEmail] = useState("");
  const [password, setPassword] = useState("");
  const [error, setError] = useState("");

  function handleSubmit(e: React.SubmitEvent<HTMLFormElement>) {
    e.preventDefault();

    if (!email) {
      setError("ایمیل الزامی است");
      return;
    }

    if (!password) {
      setError("رمز عبور الزامی است");
      return;
    }

    setError("");
    onSubmit(email, password);
  }

  return (
    <form onSubmit={handleSubmit}>
      <label htmlFor="email">ایمیل</label>
      <input
        id="email"
        type="email"
        value={email}
        onChange={(e) => setEmail(e.target.value)}
      />

      <label htmlFor="password">رمز عبور</label>
      <input
        id="password"
        type="password"
        value={password}
        onChange={(e) => setPassword(e.target.value)}
      />

      {error && <p role="alert">{error}</p>}

      <button type="submit">ورود</button>
    </form>
  );
}

تست کامل — src/components/LoginForm.test.tsx

import { describe, it, expect, vi } from "vitest";
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { LoginForm } from "./LoginForm";

describe("LoginForm component", () => {
  it.each([
    { email: "", password: "123456", expectedError: "ایمیل الزامی است" },
    { email: "a@b.com", password: "", expectedError: "رمز عبور الزامی است" },
  ])(
    'should show "$expectedError" when email is "$email"',
    async ({ email, password, expectedError }) => {
      const user = userEvent.setup();
      render(<LoginForm onSubmit={vi.fn()} />);

      // فقط فیلدهایی که مقدار دارند را پر می‌کنیم
      if (email) {
        await user.type(screen.getByLabelText("ایمیل"), email);
      }
      if (password) {
        await user.type(screen.getByLabelText("رمز عبور"), password);
      }

      await user.click(screen.getByRole("button", { name: "ورود" }));

      expect(screen.getByRole("alert")).toHaveTextContent(expectedError);
    },
  );

  it("should call onSubmit when both fields are filled", async () => {
    const user = userEvent.setup();
    const handleSubmit = vi.fn();

    render(<LoginForm onSubmit={handleSubmit} />);

    await user.type(screen.getByLabelText("ایمیل"), "a@b.com");
    await user.type(screen.getByLabelText("رمز عبور"), "123456");
    await user.click(screen.getByRole("button", { name: "ورود" }));

    expect(handleSubmit).toHaveBeenCalledWith("a@b.com", "123456");
  });
});

خروجی اجرای این تست‌ها:

✓ LoginForm component > should show "ایمیل الزامی است" when email is ""
✓ LoginForm component > should show "رمز عبور الزامی است" when email is "a@b.com"
✓ LoginForm component > should call onSubmit when both fields are filled
۱. چرا if (email) { ... } قبل از user.type؟

چون بعضی سناریوها عمداً یک فیلد را خالی می‌گذارند (مثلاً سناریوی اول password: "123456" دارد ولی email: ""). اگر بخواهیم user.type(input, "") بزنیم، عملاً هیچ کاری نمی‌کند (چون چیزی برای تایپ نیست)، ولی برای خوانایی و جلوگیری از رفتار غیرمنتظره، بهتر است صریح چک کنیم.

۲. الگوی نام‌گذاری پویا 'should show "$expectedError" when email is "$email"'

وقتی از object به‌جای آرایه‌ی ساده استفاده می‌کنید، Vitest اجازه می‌دهد مستقیم از $propertyName در اسم تست استفاده کنید. نتیجه‌اش این است که در خروجی تست، به‌جای دیدن چیزی مبهم مثل case 1، case 2، دقیقاً می‌بینید هر تست چه سناریویی را با چه مقادیری پوشش می‌دهد.

۳. چرا یک تست جدا برای حالت موفق نوشتیم؟

چون it.each بالا فقط مسیرهای خطا را پوشش می‌دهد. طبق قانون طلایی «هم مسیر موفق و هم مسیر خطا را تست کن» (بخش ۱۳)، باید حالت موفق (happy path) را هم جداگانه و مستقل تست کنیم — نمی‌شود آن را داخل همان it.each جا داد چون ساختار داده‌ی سناریوهای خطا (که انتظار پیام alert دارند) با سناریوی موفق (که انتظار صدا زده شدن onSubmit دارد) از نظر منطقی فرق دارد.

۱۹. تست کامپوننت با React Router

کامپوننت — src/pages/ProductPage.tsx

import { Link, useNavigate, useParams } from 'react-router-dom'

export function ProductPage() {
  const { productId } = useParams()
  const navigate = useNavigate()

  return (
    <div>
      <h1>محصول شماره {productId}</h1>
      <Link to="/cart">رفتن به سبد خرید</Link>
      <button onClick={() => navigate('/checkout')}>ادامه خرید</button>
    </div>
  )
}

چون از useParams و useNavigate استفاده می‌کند، باید داخل یک Router رندر شود. بهترین گزینه MemoryRouter است (یک router که در حافظه کار می‌کند، نه در مرورگر واقعی): 

import { MemoryRouter, Routes, Route } from 'react-router-dom'

function renderWithRouter(initialPath: string) {
  return render(
    <MemoryRouter initialEntries={[initialPath]}>
      <Routes>
        <Route path="/products/:productId" element={<ProductPage />} />
      </Routes>
    </MemoryRouter>
  )
}

it('should display the correct product id from the URL', () => {

  expect(screen.getByText('محصول شماره 42')).toBeInTheDocument()
})

it('should have a link to the cart page', () => {
  renderWithRouter('/products/42')
  const link = screen.getByRole('link', { name: 'رفتن به سبد خرید' })
  expect(link).toHaveAttribute('href', '/cart')
})

فلسفه مهم

به‌جای چک کردن اینکه navigate با چه آرگومانی صدا زده شده (implementation detail)، چک می‌کنیم صفحه واقعاً عوض شده — همان فلسفه‌ی «تست رفتار، نه پیاده‌سازی».

۲۰. تست کامپوننت متصل به Zustand/Redux

با Zustand (ساده‌تر، چون store فقط یک hook است)

// src/store/cartStore.ts
import { create } from 'zustand'

type CartStore = {
  items: string[]
  addItem: (item: string) => void
}

export const useCartStore = create<CartStore>((set) => ({
  items: [],
  addItem: (item) => set((state) => ({ items: [...state.items, item] })),

۲۱. مثال عملی: تست یک فلوی کامل (Integration واقعی)

یک صفحه لیست محصولات که با کلیک روی «افزودن به سبد»، هم مقدار سبد آپدیت می‌شود هم پیام موفقیت نشان داده می‌شود: 

// ProductListPage.tsx (خلاصه شده)
export function ProductListPage() {
  return (
    <div>
      <ProductList />
      <CartIndicator />
    </div>
  )
}
function renderPage() {
  const store = configureStore({ reducer: { cart: cartReducer } })
  return render(

      <ProductListPage />
    </Provider>
  )

it('should update cart indicator and show toast after adding a product', async () => {
  const user = userEvent.setup()
  renderPage()

  // قبل از هر عملی، سبد خالی است
  expect(screen.getByText('۰ کالا در سبد')).toBeInTheDocument()

  // کاربر روی دکمه افزودن اولین محصول کلیک می‌کند
  const addButtons = screen.getAllByRole('button', { name: 'افزودن به سبد' })
  await user.click(addButtons[0])

  // هم شمارنده سبد آپدیت شده...
  expect(screen.getByText('۱ کالا در سبد')).toBeInTheDocument()

  // ...هم پیام موفقیت نشان داده شده
  expect(await screen.findByRole('status')).toHaveTextContent('به سبد اضافه شد')
})
چرا این تست ارزشمند است

برخلاف unit test هایی که هرکدام یک کامپوننت را جدا تست می‌کنند، این تست تضمین می‌کند که ارتباط واقعی بین چند کامپوننت (لیست محصول ← store ← نشانگر سبد ← toast) درست کار می‌کند. خیلی از باگ‌های واقعی production دقیقاً در همین اتصال بین قطعات رخ می‌دهند، نه داخل یک کامپوننت تنها.

// src/test/test-utils.tsx
import { render, RenderOptions } from '@testing-library/react'
import { ReactElement } from 'react'
import { Provider } from 'react-redux'
import { MemoryRouter } from 'react-router-dom'
import { configureStore } from '@reduxjs/toolkit'
import cartReducer from '../store/cartSlice'

function renderWithProviders(
  ui: ReactElement,
  { preloadedState = {}, route = '/' }: { preloadedState?: object; route?: string } = {}
) {
  const store = configureStore({ reducer: { cart: cartReducer }, preloadedState })

  return render(
    <Provider store={store}>
      <MemoryRouter initialEntries={[route]}>{ui}</MemoryRouter>
    </Provider>
  )
}

// خروجی‌های testing-library را دوباره export می‌کنیم
export * from '@testing-library/react'
export { renderWithProviders as render }
